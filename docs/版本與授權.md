# 版本與授權

> 版本：0.3.1 範圍收斂稿｜2026-10-27｜產品與維護規劃；不是授權法律意見或已完成的套件稽核。
> 範圍以 [需求規格](需求規格.md) 為準：一期自營，未來僅代管 SaaS，不交付商家自行安裝版本。

## 1. 版本定義

- 七份文件目前為0.3.1範圍收斂稿，不代表目標React/FastAPI系統已完成0.1.0發布。
- 現有Sites發布號與未來程式SemVer分開記錄，保留既有版本/commit/image digest對照。
- 目標程式採SemVer：MAJOR為不相容API/資料行為、MINOR為相容新功能、PATCH為相容修正。正式營運前可用0.x，達正式驗收後才標1.0.0。
- API用`/api/v1`；破壞性變更需要版本或相容期。不能只改路徑而不處理舊前台、舊商品連結及付款回呼。
- 每次發布記錄：日期、commit、image digest、DB migration revision、設定改變、已知限制、測試報告與回滾方式。

## 3. 自有產品權利與商家合約（第三階段）

【設計提案】自有程式由業主持有，提供使用代管系統的合約權利；不提供商家source code或Docker映像下載。最終授權與法律文件仍需D-10確認，本次不擅自建立限制性LICENSE或簽定條款。

未來合約至少需要決定：

- 商家可使用的品牌/網域/帳號範圍、管理員數、空間與流量限制；目前不訂數字或收費。
- 商家資料、商品內容與客戶個資責任分工；維運者可接觸資料的條件與稽核。
- 訂閱/續約/試用/逾期/停權流程，停止服務時資料匯出格式、期限與刪除程序。
- 備份、支援時間、修復目標及可用性承諾，僅在能力與成本確認後約定，不在初稿保證SLA。
- 金流商家資格及結算：預設建議每店自行簽約與結算；平台代收分帳不在一期，不能沿用自己商家金流替所有店收款。
- 第三方服務中斷、費率變動、政策變更與不支援功能的處理。
- 商家取得圖片/品牌/商品內容權利並遵守銷售政策；系統供應者不能保證代購內容權利。

不得將平台訂閱收費與顧客商品款混成同一筆帳；SaaS訂閱計費另屬未來範圍。

## 4. 更新與維護方式

一期只營運自己的店，由業主與一位小幫手透過獨立管理員帳密操作；維護同一套服務與單一資料庫，模組化程式便於閱讀即可。RLS、跨商家管理與隔離測試延到第三階段。現貨人工填入/補貨，建單自動扣除、取消未出貨自動回補；預購不填、不扣，不納入額外庫存預留或逐項到貨模組。未來SaaS優先共享同一版本、以商家設定調整品牌，避免為每店複製一份程式造成無法升級。

發布流程：

1. 在分支完成修改，更新需求/API/DB相關文件與migration。
2. 通過相關測試、依賴與license檢查；建立固定tag與digest映像。
3. staging用備份資料去識別樣本演練升級與還原。
4. 正式備份及必要維護通知，執行相容migration，再更新映像。
5. 檢查登入、商品圖、訂單、付款回呼、備份及錯誤率，留下發布紀錄。

DB優先expand/contract：先新增相容欄位、搬資料、驗證新舊讀取，再於後續版本移除舊欄位。破壞性migration不得假設降版映像就能回滾。涉及真實付款與新訂單時先暫停寫入並對帳，再決定回復方式。

依賴更新先小版本測試，再評估大版本；安全更新按實際嚴重性加速。支援期間、修復時限、例行維護窗口及舊API退場日期待D-10。金流回呼或Google規則變更需連同整合測試，不能只跑前台build。

## 5. 商用前檢核

- 業主確認自有程式權利、外包/協作者交付條款、圖片與字型來源。
- 鎖定所有套件及容器版本，保存license、NOTICE與SBOM；處理不相容或不明授權。
- CKEditor方案及key適用實際營運；沒有key不列為已完成文字編輯功能。
- 商家金流/物流申請及服務條款有效；不宣稱未開通方法可用。
- SaaS合約、隱私、資料處理責任、帳號停權與資料匯出經確認後再對外販售。
- Docker相關工具與雲端服務費用分開評估，開源軟體不等於零營運成本。
