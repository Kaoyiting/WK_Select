## 1. 資產與責任

保護對象：會員Google身分對應、客戶聯絡資料、訂單/收件/門市快照、付款狀態、商品圖片與內容、管理權限、DB/R2/Google/金流金鑰。信用卡完整卡號與CVV不進本站，未來由金流商的託管付款介面處理。

業主負責正式帳號、管理帳號初始化、營業政策、備份與告警收件人；維運執行更新、還原與異常處理；業主與小幫手管理員同權限、個別留痕。未來平台維運跨店存取必須受控，不因是開發者就無限制讀取商家個資。

## 2. 主要風險與控制

| 風險 | 必要控制 | 驗證方式 |
| --- | --- | --- |
| 會員或管理權限遭冒用 | 前台OIDC驗證；後台獨立帳密、成熟密碼雜湊與登入限流；分離session | 錯token/錯密碼/停權/角色測試 |
| Cookie竊取或CSRF | HTTPS、HttpOnly/Secure/Lax、CSRF與Origin驗證 | API負向測試 |
| 其他客戶資料外洩 | member本人查詢、管理權限、受控R2路徑；多商家RLS延到三期 | 一期兩客戶授權測試；三期兩店隔離測試 |
| 圖片/富文字造成XSS或資源耗盡 | MIME+檔頭+像素限制、HTML清理、公開/私人資產區分 | 惡意樣本與瀏覽器測試 |
| 偽造或重複付款回呼 | 官方驗簽、商家/金額核對、事件去重、交易處理 | 沙盒及偽回呼測試 |
| 重複下單/超賣 | 後端計價、冪等、現貨同交易鎖定扣減、取消未出貨原子回補；預購不扣 | 併發/重送/回滾/欄位測試 |
| 主要儲存遺失/帳號遭刪 | 獨立加密備份與實際還原、帳號分權 | 隔離還原演練 |
| 金鑰洩漏 | 不入Git/瀏覽器、最小權限、輪替、遮罩 | secret掃描及輪替演練 |

## 3. 身分、Session與角色

- 只允許Google綁定會員下單。OIDC由後端驗證簽章、issuer、audience、expiry、nonce、一次性state與PKCE；不能只decode JWT或信任前端傳email。
- 以Google的provider+sub綁定，不以相同email/姓名合併其他會員。OAuth redirect與return_to白名單，避免開放轉址。
- 僅openid/email/profile最小scope；登入用途不保存Google密碼或不必要refresh token。
- session採高熵不透明token，DB存hash；會員cookie `__Host-wk_member_session`：HttpOnly、Secure、SameSite=Lax、Path=/，無Domain。登入成功更換session，登出/停權/權限變更可撤銷。
- session有效期與閒置期限由實作安全設定明確指定並測試；現有Worker8小時設定不是新系統已確認的永久規則。
- 所有一般寫入需要CSRF token與可信Origin；OAuth callback驗state；金流callback不用會員cookie，必須供應商簽章。
- 業主與一位小幫手以受控流程建立獨立username/password帳號，不要求Google。兩個管理員權限相同，可確認收款與退款；最後有效管理員不能被停用而鎖死後台。
- 後台以成熟套件實作密碼雜湊（提案Argon2id）、帳密驗證、限流及session撤銷，不自行發明加密。不得存明文/可逆密碼、共用預設密碼或輸出password/hash。後台cookie為`__Host-wk_admin_session`，與會員session分表、分token/CSRF，兩者不可互換。改密碼/停用撤銷admin sessions；忘記密碼一期由受控維運CLI重設，不增加email重設服務。首次密碼不得放Git或文件。
- 登入/購物/上傳各有合理限流、大小限制與逾時，正式門檻經D-08容量確認，不以阻擋正常客戶為目標。

## 4. 資料及租戶隔離

一期只服務自己的店，tenant_id是伺服器固定設定，沒有商家切換或公開開店；不建立tenant_memberships、RLS、跨店lookup角色或兩店測試。會員本人訂單授權與管理員帳密權限必須在一期完成。第三階段才設計可信host、租戶複合外鍵、RLS與連線池隔離；未完成不得讓多商家共用資料庫營運。

資料庫只在內網，migration/backup/runtime分角色。API回應與日誌最小化個資；公開CMS必須白名單，不能整張settings或整個user模型直接serialize。會員/商家資料實體刪除、匯出、保存期限與停權政策待D-06/D-10；未確認前不寫自動刪除客戶的排程，也不承諾無限期保存。

## 5. 上傳、編輯器與瀏覽器

- 本地上傳與剪貼簿圖片走同一驗證與R2寫入流程；每檔<=5MB，允許JPEG/PNG/WebP/GIF，檔名/Content-Type不能取代檔頭驗證。
- 驗證可解碼、尺寸與總像素，設技術上限以防解壓炸彈（初步提案40MP，實測後固定）。SVG/HTML不作商品圖片上傳。
- 先給local blob預覽，再用成功上傳資產URL；不能持久化blob、本機路徑或任意外部URL當內部資產。
- R2 object_key由伺服器產生並含環境/tenant，公開商品與私人檔案分離；草稿預覽需管理權限。快取不得將私人檔案公開。
- 不自動抓取人工代購URL圖片；將來若需要抓取另設SSRF防護與來源授權，本期不做。
- CKEditor輸出HTML仍須後端白名單清理；不因是管理員內容就允許script/onerror/javascript URL。不要用正規表示式取代HTML sanitizer。
- 設定CSP、X-Content-Type-Options、Referrer-Policy與frame限制；CSP依實際Google/CKEditor/R2來源列出，勿用全面放行解決載入問題。
- 富文字工具、金鑰適用條款與第三方圖片權利依 [版本與授權](版本與授權.md) 確認。

## 6. 線上金流與虛擬帳號

串金流會增加回呼驗證、狀態/重試、對帳、憑證與退款風險。採金流商託管付款頁，可減少本站直接接觸卡片資料的範圍，但仍需完成服務商規定的安全與合規要求，不等於免除資安責任。

虛擬ATM帳號可透過有提供此服務的金流商取得；綠界是候選，不是唯一選擇。操作規劃：申請商家帳號→依身分/公司資格提交審核→開通ATM及需要的付款方法→取得測試/正式憑證→沙盒建單取號→接收取號通知→顧客匯款→接收並核驗付款通知→對帳。資格、費率、撥款日、帳號期限及可用方法以實際合約為準（D-04）。本站不自行發銀行帳號，也不只憑買家說已匯款就標paid。

- 取號成功是pending；已驗證成功入帳才paid。瀏覽器回跳不作付款證據。
- 檢查簽章、MerchantID、MerchantTradeNo、金額與既有付款紀錄，使用建立交易時的credential_ref驗證。
- 回呼先完成持久化交易再ACK；重送只有一次業務效果。未知/錯簽章/錯金額不回成功ACK。
- 延遲入帳或取消後入帳記錄實際款項並人工處理，不自動恢復訂單或重新扣庫存。
- 手動轉帳由登入管理員核對實際銀行入帳；手動退款記錄必須對應已發生退款，不假裝發出銀行或金流退款。
- 金流建單不確定成功時先查詢既有交易；不得新建交易以「重試」而造成重複付款。
- 金流商密鑰不上前端、不入完整日誌；線上金流正式開關預設關閉。

## 7. 金鑰與環境管理

| 項目 | 控制 |
| --- | --- |
| DB | runtime/migration/backup/bootstrap不同帳密；DB無公網port；連線與備份加密 |
| Google | local/staging/prod各自OAuth client或明確隔離設定；redirect完全對應 |
| R2 | 限必要bucket/操作，不使用帳號總權限key；備份用獨立帳號或受控目的地 |
| 金流 | 測試與正式分開；僅API/受控工作可讀；付款保存credential_ref便於輪替期間對應 |
| Session | 高熵secret，與其他用途分離；輪替可使既有session失效並要求重登 |
| CI/CD | 最小部署權限、不得讀回完整正式個資；映像/鎖檔固定、審核變更 |
| Compose secrets | 每服務只掛需要檔案；主機檔案權限受控，另做磁碟/備份加密；不是自動加密保險箱 |

真實.env/secrets/private keys/dumps不可進Git、截圖、聊天或公開錯誤輸出。不得把secret放進VITE_*。輪替流程：建立新憑證→staging驗證→受控部署→核對仍有效交易/回呼→撤銷舊憑證→稽核記錄。金流舊交易驗簽需要保留多久及平台是否允許多組key，須與供應商確認，不臆測。

## 8. 備份目標與範圍

【設計提案，D-08未定SLA】起步每日資料庫邏輯備份，目標RPO24小時、RTO4小時；若不能接受最多一天訂單資料損失，正式前改更頻密備份或WAL/PITR。主機壞掉時的容量、重建時間須演練，不能以「有dump」宣稱可滿足目標。

| 備份內容 | 方法及注意 |
| --- | --- |
| PostgreSQL資料/schema | pg_dump custom format、migration revision與清單；保持交易一致性，核對單店全部必要資料；第三階段再核對各tenant |
| DB角色/權限 | 保存角色建立腳本與必要設定；含密碼hash的匯出也視為秘密加密保管 |
| R2及舊靜態圖片 | 定期複製物件到獨立受控目的地，保存object_key/size/hash清單；不假設已開版本保留或自動複寫 |
| 設定與秘密 | 版本化非秘密設定；secret另加密備份，解密鑰分開保存且至少兩個受控恢復管道 |
| 程式及部署 | Git遠端與固定映像digest/依賴鎖檔；程式備份不等於訂單備份 |

容器volume、同主機另一資料夾、同帳號同bucket複本都不能作為唯一災難備份。主要帳號遭刪除時仍要有可用副本。建議保留每日7份/每週4份/每月3份，屬容量及保留期提案，需配合D-06/D-08確認，未確認不對外承諾。

備份使用受控工具容器、pgpass/secret檔案，不將完整連線密碼放命令列或shell歷史。一期備份角色僅需完整讀取本店資料與schema，僅供排程使用而不給常駐應用；不為未實作的RLS配置BYPASSRLS。三期啟用RLS時再補受控全租戶備份權限與完整性測試，避免少備份。pg_dump本身不提供完整PITR與自動災難恢復方案。

DB與R2不是同一個原子快照；備份作業要記錄快照時間與asset清單，暫停刪除/保留安全緩衝或短暫凍結上傳，確保清單中物件均可還原。孤立多餘圖片可以後續清理，不能遺失訂單引用圖片。

## 9. 備份與還原作業流程

### 每次備份

1. 排程取得互斥鎖，記錄開始時間、版本、tenant/關鍵表筆數；失敗不能被下一次覆蓋而無人知曉。
2. 以專屬備份角色產生一致性dump，保存schema revision與物件清單；壓縮/加密後傳到獨立目的地。
3. 產生checksum，檢查檔案可讀、非空、manifest物件齊全；只看檔案存在不足夠。
4. 成功後才按確認過的保留政策清除舊備份；失敗保留證據並告警。
5. 日誌不含敏感個資/金鑰；監控最後成功備份時間、大小異常及目的地權限。

### 隔離還原演練

1. 選定備份及目標版本，核准恢復範圍；建立新的隔離DB與bucket，不覆蓋正式環境。
2. 取回解密金鑰、驗checksum與manifest；還原角色/schema/data，記錄開始與完成時間。
3. 使用對應版本程式，停用對外付款、通知與定時工作，避免重送真實交易；還原資料不觸發建單事件。
4. 核對單店各表筆數（第三階段另核對各tenant）、訂單總和、FK、會員/角色、庫存、付款事件及圖片可讀性。
5. 測Google會員本人訂單與跨客戶拒絕、兩位帳密管理員登入；會員/admin及測試/正式session不混用。三期才測跨商家。
6. 量測RPO/RTO，記錄缺陷與修復；新系統上線前至少成功一次，後續建議每月抽樣還原、重大migration後完整演練，頻率D-08確認。
7. 真正災難切回前暫停寫入，與銀行/金流核對備份後交易，補齊差異再恢復服務。不可把restore成功當成付款帳已平。

不提供本次可直接覆蓋正式DB的還原命令；具體腳本必須先在隔離環境實作驗證，再納入發布流程。

## 10. 稽核、日誌與事故處理

稽核至少涵蓋：admin指派及撤銷、登入異常、上下架、價格/庫存變更、導航/CMS發布、人工需求、訂單轉移、付款確認/退款、出貨、金鑰更換、資料匯出/還原。保留actor、tenant、target、時間、request_id與遮罩前後值；不存完整ID token、cookie、卡號、密碼、金流key或不必要完整收件資料。

應用角色對audit_logs只有INSERT/SELECT；DB高權限仍可能改資料，不能稱為絕對不可竄改。未來可加獨立受限儲存的定期稽核匯出與hash核對。保存期與可查詢人員待D-06/D-10。

| 事件 | 立即處理 | 恢復前確認 |
| --- | --- | --- |
| 金鑰外洩 | 撤銷/輪替，停止受影響整合，保留證據 | 存取範圍、異常交易、備份與程式是否被修改 |
| 客戶資料外洩（三期含跨店） | 限制受影響API，保全日誌，確認範圍 | 修復權限、兩客戶負向測試（三期加兩店）、依適用規定處理通知 |
| 偽付款或金額異常 | 停止自動標paid/出貨，人工對帳 | 回呼驗簽、重送、已出貨/退款例外清單 |
| DB損毀/主機故障 | 停止寫入，從驗證備份隔離還原 | 備份後訂單及實際入帳差異，避免重複收款 |
| R2故障 | 阻止壞圖發布、保留上傳重試狀態 | 物件可讀性與DB資產對照，不將失敗當成功 |

事故負責人、通知管道、處理優先級與時限須D-08指定。法律/消費政策、個資告知、取消與退換貨條款應依實際業務確認；不得把其他賣場的免責文字當成本站合規保證。

會員密碼採 Argon2 雜湊、不回傳前端。會員及管理員 session 保持分離。帳密登入沿用 Origin 與 HttpOnly cookie 保護；每個來源與帳號 15 分鐘內最多 8 次失敗登入。自動信箱驗證與重設信尚未接通，正式上線前需完成寄信服務或確認人工帳號復原流程。


### 2026-10-28 訂單詳情與常用門市

## 2026-10-29 STAGE 金流邊界
測試公開憑證僅能影響 is_test=true 的測試訂單，production 拒絕 stage callbacks 與 ecPay_atm_test 建單。測試訂單不得實際出貨。正式金流需獨立憑證與 SimulatePaid 防護，未在此版開放。
付款資訊透過會員所有權或管理員權限查閱；供應商回傳不使用 cookie CSRF，改驗證 CheckMacValue、商店／金額／ATM 類型／交易編號。付款通知與取消使用同一訂單鎖；通知重送不重複入帳或扣庫存。
測試排程的到期時間使用資料庫，不放瀏覽器 timer。重啟後掃描到期訂單，綠界查詢失敗時保守保留庫存，需監控 worker 警告。備份須包含新訂單期限與交易對應欄位。
